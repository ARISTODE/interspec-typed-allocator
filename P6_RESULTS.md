# P6 Representative Results

This file records one reproducible CI evaluation run for the P6 implementation. The purpose is to preserve a concrete reference point, not to turn shared hosted runner timing into a universal performance claim.

Reference implementation commit:

```text
4136b14a6ee2237c156a6ba939a0e2374aa5de2f
```

Reference CI environment:

```text
Ubuntu 24.04 hosted runner
GNU C++ 13.3.0
INTERSPEC_BENCH_ITERATIONS=100000
```

## 1. Security matrix

All 25 evaluated cases passed.

The passing cases include correct type acceptance, interior pointer validation, wrong type rejection, allocation bound enforcement, untracked pointer rejection, exact base release, stale pointer rejection after free, stale pointer rejection after successful realloc, type preservation across realloc, C realloc failure semantics, unknown TypeId rejection, zero size allocation rejection, TypeHash collision rejection, and invalid arena rejection.

The security CSV is generated by `evaluation/security_eval.cpp` and is uploaded as part of the `p6-evaluation-results` CI artifact.

## 2. Single threaded lookup scaling

Representative `check_live` results from the same hosted runner are:

| Live tracked allocations | ns per check | checks per second |
| ---: | ---: | ---: |
| 1 | 11.76 | 85,044,210 |
| 16 | 13.90 | 71,951,039 |
| 256 | 20.52 | 48,723,303 |
| 4,096 | 31.83 | 31,421,572 |
| 16,384 | 82.92 | 12,059,642 |

The population sweep is consistent with the expected logarithmic lookup structure, but the absolute values are specific to this run and machine. They should not be compared directly with measurements from unrelated hardware.

The other read side operations showed similar scale in this run. At 16,384 live allocations, interior checks measured 81.91 ns per operation, wrong type rejection measured 81.74 ns per operation, and remaining extent lookup measured 82.19 ns per operation.

## 3. Allocation and concurrent checks

Creating 16,384 tracked allocations measured 86.24 ns per allocation in this run.

For a 4,096 allocation metadata set, representative aggregate read only check throughput was:

| Trusted threads | Aggregate checks per second |
| ---: | ---: |
| 1 | 24,950,923 |
| 2 | 33,055,240 |
| 4 | 20,389,057 |
| 8 | 21,946,962 |

The hosted runner does not show monotonic throughput scaling beyond two threads. P6 therefore does not claim linear concurrency scaling. The important concurrency claim is correctness and safe shared metadata access; controlled hardware measurements are required for a meaningful throughput scaling study.

## 4. Release smoke test

The same CI revision successfully built the installable CMake package, installed it into a clean staging prefix, configured a separate consumer project through `find_package(interspec-runtime CONFIG REQUIRED)`, linked the consumer against `interspec::runtime`, executed the consumer successfully, and produced the `interspec-typed-allocator-0.1.0.tar.gz` research preview archive with a SHA256 checksum.

## 5. End to end regression

The P6 branch retains the required RLBox + NaCl job from P4c. The final P6 merge is accepted only after that job and the CodeQL policy inference gates remain green together with the core, evaluation, and release smoke jobs.
