_Software compartmentalization_ is a design principle that hardens application security by enforcing the _principle of least privilege_ [protection-info-system, sok-compartmentalization]. A compartmentalized application divides its code and data into distinct _compartments_, each executing within a separate protection domain with access only to the resources and permissions it strictly requires. A growing body of work isolates libraries, drivers, and kernel subsystems using mechanisms such as process isolation [provos2003preventing], WebAssembly sandboxing [rlbox, isolation-without-taxation], software fault isolation (SFI) [xfi, bgi], hardware memory protection and memory tagging [erim, hacks, bulkhead], and virtualization [ksplit, lvds, lxds]. By confining each component to a distinct domain, these systems reduce the damage caused by a compromised component. Compartmentalization is also retrofitted into existing software, including browser libraries [rlbox] and kernel drivers [sud, hacks, bulkhead, nooks, microdrivers, ksplit, lvds, lxds]. Where it has been deployed, it has reduced the impact of real vulnerabilities. For example, the sandbox compartments of OpenSSH and slaacd in OpenBSD have mitigated code-execution flaws [sok-compartmentalization].

However, isolation alone does not make a compartmentalized application secure. While isolation mechanisms prevent compartments from directly accessing other compartments' memory, compartments still communicate through a _compartment interface_. It consists of a set of functions that other compartments can invoke, shared state, and the data exchanged through function parameters and return values [sok-compartmentalization, assess_civ]. A compromised compartment can therefore attack other compartments not by escaping the isolation mechanism, but by abusing the data that the interface legitimately exposes. Prior work has found such flaws in real software. In Firefox, a sandboxed image library could read and write arbitrary memory of the renderer if the renderer did not check callback arguments [rlbox]. Similarly, a sandboxed libghostscript can write to arbitrary memory of ImageMagick, and an attacker can extract the keys of an isolated OpenSSL through a single interface flaw [assess_civ]. These attacks do not need to hijack control flow. Corrupted data alone, such as a pointer that the application later dereferences, is enough [dui].

Lefeuvre et al. [assess_civ] term such flaws _Compartment Interface Vulnerabilities_ (CIVs). CIVs are instances of the confused-deputy problem [hardy1988confuseddeputy], where an untrusted compartment manipulates the interface so that a trusted compartment misuses its authority on the attacker's behalf. They are also common. Lefeuvre et al. found 629 potential CIVs in 39 compartmentalization scenarios across 25 applications [assess_civ], and a study of 11 Linux drivers under isolation finds several classes of CIVs prevalent across these drivers [huang_sok_attack_surface_device_drv_iso].

P4 [words 170, offset 398, 33%]
Prior work has made significant progress in understanding this attack surface. It classifies CIVs, detects them with fuzzing and program analysis, and measures their prevalence at candidate boundaries in applications and the Linux kernel [assess_civ, civscope, dui, huang_sok_attack_surface_device_drv_iso]. Protecting against CIVs, however, remains largely manual. Lefeuvre et al. observe that almost all compartmentalization frameworks neglect the problem of securing interfaces and that even RLBox relies extensively on manual checking [assess_civ]. The RLBox authors report that writing these checks was the hardest part of retrofitting Firefox [rlbox]. Microdrivers [microdrivers] and KSplit [ksplit] selectively synchronize shared state, which can reduce oversharing. However, they are primarily designed for compatibility and performance and do not infer security policies for CIV protection at field granularity. Runtime monitors check invariants inferred from observed executions [microdriver+], and inferring sound and complete invariants remains challenging [huang_sok_attack_surface_device_drv_iso], and LXFI [Mao11LXFI] relies on manually specified rules. *As a result, the data that crosses a compartment interface remains a largely unprotected attack surface, and protecting it is left to the developer.*

P5 [words 143, offset 568, 48%]
This paper aims to close this remaining attack surface automatically. We focus on _insecure data-flow_ CIVs, which leak or corrupt interface data and account for most of the CIVs that these studies report [huang_sok_attack_surface_device_drv_iso, assess_civ]. CIVs that abuse the order or timing of interface calls are outside our scope. _Data leakage_ occurs when a trusted compartment exposes more interface data than an untrusted compartment needs. _Data corruption_ occurs when an untrusted compartment modifies interface data that a trusted one later uses. Preventing both requires three decisions for the data that crosses an interface: what data may be passed from a trusted compartment into an untrusted one, which updates from the untrusted compartment may affect the trusted state, and which pointer values require validation before the trusted compartment dereferences them. Our goal is to make these decisions automatically and to enforce them at runtime.

P6 [words 145, offset 711, 60%]
We present InterSpec, a framework for inferring and enforcing policies for interface data flow in a compartmentalized application. Given an interface between a trusted and an untrusted compartment, InterSpec analyzes how each side accesses interface data, then derives confidentiality and integrity policies at field granularity. Built on a Program Dependence Graph (PDG) [Ferrante87PDG, LiuTJ17Ptrsplit], InterSpec uses static analysis to infer three policies: (1) a _least-privilege read_ policy (SP1) that prevents unnecessary data exposure to the untrusted compartment, providing confidentiality, (2) a _least-privilege write_ policy (SP2) that prevents the untrusted compartment's unauthorized updates from affecting trusted state, providing integrity protection, and (3) a _pointer integrity_ policy (SP3) that validates untrusted pointer values before the trusted compartment dereferences them. SP3 checks that each pointer refers to a live object of the expected type in the expected compartment's memory and that the access stays within the object's bounds.

P7 [words 193, offset 856, 72%]
InterSpec enforces these policies by generating wrappers around compartment interface calls, integrated with the RLBox framework [rlbox]. For interface data protected by SP1, the wrapper does not pass that data to the untrusted compartment. For interface data protected by SP2 and SP3, the wrapper either does not copy possibly corrupted data back to the trusted compartment or validates it before trusted use. To validate pointer values, InterSpec keeps a trusted object registry that records the type, bounds, and lifetime of known objects in both compartments' memory. Our key contributions are listed below. • We analyze insecure data-flow CIVs and define three security policies (SP1, SP2, SP3) that address data leakage, data corruption, and pointer integrity (Section X). • We design and implement a static analysis framework that infers these policies from a compartment boundary specification by analyzing how trusted and untrusted compartments access interface data (Section X). • We integrate the inferred policies with RLBox by generating boundary wrappers that restrict data sharing at field granularity and validate pointer values against a trusted object registry (Section X). • We validate the enforced policies against representative data-leakage, data-corruption, and pointer redirection violations (Section X).

P8 [words 144, offset 1049, 88%]
We evaluate InterSpec on 10 library isolation boundaries, six in the applications FFmpeg, memcached, Nginx, and rsync and four in programs that use libpng, libucl, libyaml, and libzip (Section X). Averaged over the boundaries, the inferred policies provide confidentiality coverage for 49.0% of interface fields and integrity coverage for 59.3%. On average, 99.98% of pointer fields either need no runtime validation or have an inferred expected domain (Section X). Relative to an RLBox sandboxing baseline, InterSpec adds 0.8% on average to complete programs, and its overhead is within measurement variation in 11 of 15 workloads. In library stress workloads, which call the sandboxed library without application work in between, it ranges from -6.7% to 8.6%. At the low end, the policies remove a copy. At the high end, each query takes about 120 ns and returns two pointers that must be checked (Section X).
